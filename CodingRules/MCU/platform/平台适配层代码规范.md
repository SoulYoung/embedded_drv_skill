# 平台适配层代码规范

## 1. 适用范围与层级契约

本规范适用于把通用软件能力部署到某个硬件平台的适配层。平台可以是开发板、量产板、模组、Boot 运行环境或另一种系统组合。该层负责设备实例映射、引脚/电源默认态、启动顺序、驱动绑定、句柄管理和事件桥接。

平台层向下调用 MCU 驱动层和外设器件驱动层，向上提供不暴露具体硬件的统一接口。不得直接操作寄存器，不实现具体外设协议，不承载产品业务策略；这些职责分别属于驱动层、器件层和应用层。

## 2. 文件与配置组织范式

- 文本统一 UTF-8。实现文件建议为 `brd_<module>_<platform>.c/.h`；若平台名由目录隔离，文件可省略平台后缀。配置、定义和实现分别置于 `cfg/`、`def/`、`src/` 或项目既有等价目录。
- 通用 API 放公共接口目录，平台私有头只暴露平台配置、属性对象和初始化入口。头文件采用 Doxygen 文件头、唯一 guard 和 C++ 兼容块。
- 平台差异必须数据化：引脚、设备类型、总线实例、地址、电平极性、电源依赖和默认配置应进入静态配置表，不散落在条件编译或函数体中。
- 为每个模块明确依赖顺序（时钟/电源 → 引脚 → 总线/驱动 → 外设 → 上层服务）；跨模块依赖需要在 Init/Done 注释中说明。

## 3. 命名与实例模型

项目可保留既有前缀；推荐如下范式：

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 类型 | `Brd_T` + PascalCase | `Brd_TUartItem` |
| 常量 | `kBrd` + PascalCase | `kBrdModuleShiftUart` |
| API | `Brd_` + 模块 + 动词 | `Brd_UartOpen` |
| 私有函数 | `Brd_` + 模块 + 动词 + `static` | `Brd_UartGetIndex` |
| 属性表 | `g_brd_` + 模块 + `_attr` | `g_brd_uart_attr` |
| 回调 | `On` + 事件 PascalCase | `OnRecv` |

多实例模块采用 `Attr → Item → DevCfg`：`Attr` 管理数量和条目数组；`Item` 保存逻辑 ID、实现类型、运行状态和专属配置指针；`DevCfg` 描述某种实现所需的底层配置。逻辑 ID 对上层稳定，数组下标和具体总线实例仅在平台内部使用。

## 4. 初始化、句柄与资源管理

- `Init` 按依赖顺序建立安全默认态；`Done` 以严格反向顺序停用设备、释放驱动、恢复引脚/电源和清理状态。重复调用的行为必须明确。
- 未打开设备的引脚必须处于安全状态：输出初始电平先于输出使能设置；输入/输出方向、上下拉、复用、电源开关和唤醒源需与硬件原理图一致。
- 句柄由“模块类别 + 实例索引/ID”编码或由对象池分配。所有解码结果都要先验证类别、索引范围和条目有效性，再访问条目。
- Open 只在状态合法、依赖就绪时绑定并打开下层对象；任何步骤失败都撤销本次已完成动作。Close/Destroy 解除回调、停止活动传输、关闭器件/驱动并重置状态。
- 配置表原则上 `const`；运行态仅写入 Item 私有字段。禁止让应用层直接修改平台配置表或持有底层驱动指针。

## 5. 驱动绑定与事件桥接

- 根据 `Item` 的设备类型选择内部外设、外接器件或模拟实现；类型转换前检查配置指针和类型标识。
- 回调桥接函数必须为 `static`：从注册上下文恢复条目，校验条目、状态和上层回调后，把平台句柄及必要数据转发。回调入口不得泄漏底层对象指针。
- 回调中禁止阻塞、递归打开/关闭同一设备、长临界区和直接寄存器访问；需要延后处理时投递事件到任务/队列。
- 回调注册与注销必须同生命周期对称，Close/Destroy 后不得再调用已失效的上层函数指针。

## 6. 控制流、错误与格式

- 使用项目统一的基础类型与错误码。新增可失败函数采用单出口：先检查句柄/参数/状态，再执行底层调用，最后唯一 `return result;`。
- 将驱动/器件错误转换或透传为平台 API 承诺的错误语义；不得丢失参数、状态、通信、超时和资源冲突等关键信息。
- 所有 GPIO、ID、数组索引、总线地址及配置指针在使用前验证。禁止因配置错误而越界、空解引用或误驱动输出。
- 采用第 7 章定义的统一 C 风格。注释须说明硬件约束、初始化次序和状态变化原因。

## 7. 平台层编码细则（强制）

### 7.1 配置表和结构体

- 引脚、极性、设备地址、总线实例、依赖关系等配置使用 `static const` 表和 C99 指定成员初始化；每个字段用行尾注释给出单位或含义。
- 配置结构与运行态结构分开。配置表不可写，`Item` 中仅保存 `opened_`、`enabled_`、回调上下文等可变状态。
- 不使用裸数组下标访问配置：先验证 `index >= 0`，再将其转换为无符号与 `count` 比较；计数类型与数组大小类型保持一致。

### 7.2 `if/else` 与错误路径

- 按“句柄/指针 → 索引/配置 → 生命周期状态 → 下层调用”顺序写条件。`if`、`else if`、`else` 分支仅一条语句时不得加花括号；分支包含两条及以上语句时必须加花括号，包括引脚、供电和回调注册等场景。
- 可失败接口以 `result` 单出口收敛；不要在中途 `return`，也不要用嵌套三目表达式决定错误码。对下层失败，先保留错误语义，再执行必要回滚。
- 设备未配置、类型不匹配、句柄非法均作为可预期错误处理；不能因“配置理论上正确”而省略运行时检查。

### 7.3 `switch` 与设备分派

- `switch (item->type)` 是平台绑定的首选分派形式。每个 `case` 使用花括号，完成类型转换、空检查和一个实现分支后 `break;`。
- `default` 必须设置“不支持/配置错误”结果；禁止默默忽略未知设备类型。禁止无注释 case 贯穿。

```c
switch (item->type)
{
case kBrdDeviceInternal:
{
    result = Brd_XxxOpenInternal(item);
    break;
}

case kBrdDeviceExternal:
{
    result = Brd_XxxOpenExternal(item);
    break;
}

default:
    result = kBrdErrorNotSupport;
    break;
}
```

### 7.4 Init/Done 的书写顺序

- Init 中每一项按“安全电平 → 方向/上下拉 → 复用 → 电源/时钟 → 下层对象 → 回调”处理；实际硬件要求不同的顺序必须注释理由。
- Done 反向执行，先停止事件来源和回调，再关闭设备，最后恢复引脚和电源。失败清理不得触发上层回调。
- 循环初始化每次只处理一个 Item。索引递增或递减必须与模块现有依赖约定一致；不得使用无符号递减循环。

### 7.5 通用排版规则

- 4 空格缩进，左花括号换行，指针随类型书写；一行只声明一个变量。控制关键字后空格，二元运算符两侧空格。
- `for` 用于固定条目遍历，`while` 仅用于状态条件。回调、锁和寄存器访问不得位于长循环内部。
- 常量使用具名枚举或 `static const`，布尔字面量使用工程统一值。宏仅用于头文件常量或安全的通用表达式，禁止宏中隐藏副作用。
- 平台公开 API、配置字段、回调桥接均需中文 Doxygen；注释应描述电气安全、资源所有权或事件上下文，而非重复函数名。

## 8. 生成前检查清单

1. 是否只包含平台绑定逻辑，而没有寄存器实现、外设协议或业务决策？
2. 是否用静态配置表表达硬件差异，并保证逻辑 ID/API 对上层稳定？
3. Init/Done、Open/Close、回调注册/注销、引脚/电源状态是否完全对称？
4. 句柄解码和配置访问是否在任何数组/指针使用前完成验证？
5. 回调是否只桥接事件、无阻塞，并避免暴露下层对象？
6. Init/Done、`if/else`、`switch`、循环与配置表是否满足第 7 章的具体风格？
