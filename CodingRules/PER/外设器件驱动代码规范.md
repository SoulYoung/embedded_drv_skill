# 外设器件驱动代码规范

## 1. 适用范围与层级契约

本规范适用于通过 I2C、SPI、UART、CAN、单线或 GPIO 连接的独立外设器件驱动，例如存储器、RTC、传感器、显示器、收发器和安全器件。器件层实现具体器件的数据手册协议、命令、寄存器、时序、容量和型号差异。

器件驱动不得绑定任何 MCU、板卡、RTOS 或产品。总线传输、延时、锁、日志和电源控制通过注入的回调/适配接口获得；因此同一器件驱动应能被不同 MCU 和平台复用。

## 2. 目录、文件与接口分层

- 使用 UTF-8。按“类别/通用接口/器件型号”组织：`per/<category>/common` 保存跨型号接口，`per/<category>/<device>` 保存具体实现。文件名建议 `per_<category>_<device>.c/.h`；兼容或扩展 API 使用 `_ex` 后缀。
- 公共接口头定义数据模型、错误码、总线回调和通用能力；芯片头只声明该器件的对象、配置和功能。每个头文件具备 Doxygen 文件头、guard 与 `extern "C"`。
- 公开 API 以设备语义命名，如读时间、读取标识、擦除块、设置工作模式；不暴露总线命令拼包细节。命令包、寄存器地址和私有读写函数放 `.c`。

## 3. 命名和对象范式

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 器件对象 | `TPer` + 类别 + 型号 PascalCase | `TPerRtcXxx` |
| 公共类型 | `TPer` + 类别 + 名称 | `TPerFlashInfo` |
| 错误码 | `kPer` + 类别 + 错误名称 | `kPerRtcErrorComm` |
| 命令/寄存器常量 | `k` + 器件/类别 + 名称 | `kRtcRegSecond` |
| 公共函数 | `TPer` + 器件 + 动词 | `TPerRtcXxxGetTime` |
| 私有函数 | 同模块前缀且 `static` | `TPerRtcXxxReadByte` |
| 回调成员 | `On` + 操作 PascalCase | `OnTransfer` |

对象包含 `user_data`、所需回调、不可变配置及私有运行态；私有字段使用小写下划线和 `_` 后缀。公共结构字段顺序、枚举数值、回调签名和错误码语义一旦发布不得破坏。

## 4. 回调注入与生命周期

- 通用接口先定义传输回调。回调第一个参数为 `void *user_data`，驱动原样回传；回调应支持总线写、读、写后读和必要的等待/延时，但不依赖特定 MCU 驱动类型。
- Create 初始化所有成员和回调；Open 验证回调、读取器件 ID/状态、识别容量或版本并执行默认配置；Close 停止需要停止的模式并清除打开状态；Destroy 释放对象资源。
- 每次总线传输都必须处理失败。回调返回值由本层统一映射为器件错误码，不让上层依赖某一平台的错误码。
- 对象的 `opened`、`busy`、擦写/转换进行中等状态需显式维护。Open/Close 失败应保持状态一致；异步操作结束、取消和失败都必须清理 busy 状态。

## 5. 协议、边界和可靠性

- 命令、寄存器地址、状态位、页/块大小、最大重试次数和超时使用文件顶部的具名常量；注释写明数据手册来源、单位和适用条件。
- 用私有读写助手封装重复的命令帧、字节序和校验；公开 API 只组合这些助手实现设备功能。多型号容量和地址宽度使用 `static const` 描述表或明确分支，禁止散落魔法数。
- 先校验对象、缓冲区、长度、偏移、地址对齐、页/扇区边界和打开状态。区间校验必须避免算术溢出，跨页/跨块写入必须拆分并逐段更新地址和指针。
- 轮询写入完成、转换完成或设备就绪必须有超时/重试上限；等待期间若提供等待回调，应允许上层调度。禁止无限轮询。
- 写入/擦除前检查写使能和保护状态；失败时返回明确错误并尽可能读取状态寄存器辅助诊断。对掉电敏感操作，在接口说明中写清原子性和恢复要求。

## 6. 错误、控制流和格式

- 公开可失败函数使用单出口：依次处理参数、回调、状态和传输结果，最后唯一 `return result;`。`void` 接口只用于确实无错误可报告的动作。
- 错误码至少区分参数错误、回调未配置、未打开/忙、通信失败、超时、不支持、校验失败和器件状态错误（按类别裁剪）。
- 使用项目统一的定宽整数和布尔类型；具体书写风格遵循第 7 章。公开 API 均使用中文 Doxygen 描述单位、输入输出、前置条件、并发约束和错误码。
- 传输逻辑应可替换为 Mock 回调测试。测试应覆盖：ID 识别、回调失败、超时、参数越界、跨页/跨块、忙状态和正常读写。

## 7. 器件协议编码细则（强制）

### 7.1 文件布局、常量与命令帧

- `.c` 内按“包含 → 命令/状态常量 → 型号表 → 私有函数声明 → 公开 API → 私有协议助手”排列。命令值使用十六进制，容量、超时和页大小使用带单位的具名常量。
- 命令帧使用局部 `UInt8 cmd[]` 或明确的帧结构组装；写入每个字节时注释字节序、地址宽度或控制位。禁止复用含旧数据的未完全初始化缓冲区。
- 读写助手只处理总线传输和命令帧，公开函数只处理设备语义、参数和状态。重复的地址编码、校验或状态读取必须提取为 `static` 函数。

### 7.2 `if/else`、轮询与状态

- 条件顺序固定为：`self`/缓冲区 → 长度/范围/对齐 → 回调是否注册 → 是否已打开/忙 → 总线操作。每个失败分支只设置一次对应错误码。
- `if`、`else if`、`else` 分支仅一条语句时不得加花括号；分支包含两条及以上语句时必须加花括号。成功与失败分支均更新运行状态；禁止在传输成功后忘记清 busy，也禁止在失败路径留下写使能或临时模式。
- 轮询统一采用剩余次数或截止时间；循环体中先读取状态、判断完成、再递减计数。耗时等待调用注入回调或平台延时接口，不能无延时紧密自旋。

```c
while (remain > 0U && result == kPerErrorSuccess)
{
    result = TPerXxxReadStatus(self, &status);
    if ((result == kPerErrorSuccess) && ((status & kPerStatusBusy) == 0U))
        completed = True;
    else
        remain--;
}
```

循环结束后必须根据 `completed` 和 `result` 返回成功、通信错误或超时，不能把未完成误报为成功。

### 7.3 `switch`、型号与地址分派

- 用 `switch` 分派器件模式、地址宽度或识别出的型号；每个 `case` 使用花括号隔离局部变量，并以 `break;` 结束。未知型号进入 `default` 并返回不支持错误。
- 型号仅对应数据驱动差异（容量、页大小、命令变体）；同一协议流程不要复制多份。优先查 `static const` 描述表，只有流程确实不同才使用 `switch`。
- 禁止 case 贯穿；若数据手册要求共享流程，在 `case` 组前说明原因，或提取共同私有函数。

### 7.4 指针、长度与字节序

- 指针随类型书写，一行只声明一个变量；输入数据使用 `const void *`，输出数据使用 `void *`。在将 `void *` 转为字节指针后，按每次成功传输量更新指针。
- 缓冲区区间用不溢出的形式检查，例如先验证 `offset <= capacity`，再验证 `size <= capacity - offset`。禁止只判断 `offset + size <= capacity`。
- 多字节整数的拆装必须明确高低字节顺序；移位前转换到足够宽的无符号类型，掩码和移位次数均具名或有注释。

### 7.5 公共风格与注释

- 4 空格缩进、左花括号换行、控制关键字后空格、二元运算符两侧空格；超长调用在逗号后换行。局部变量声明靠近首次使用处并立即初始化。
- 函数以单出口返回；`goto`、隐藏副作用宏、嵌套三目表达式和在条件中执行传输均禁止。常量优先枚举/`static const`，宏必须带完整括号且不重复计算参数。
- 注释记录协议依据、时序/单位、掉电后果、状态位含义及重试原因。对公开接口说明线程/回调上下文、缓冲区所有权和可恢复性。

## 8. 生成前检查清单

1. 是否仅实现器件协议，且完全不依赖特定 MCU、板卡或 RTOS？
2. 总线和等待能力是否均通过注入回调取得，回调错误是否映射为器件错误码？
3. 命令、地址、状态位、超时和容量是否具名化并能追溯数据手册？
4. 是否对所有长度、地址、边界和异步状态做验证，且等待可终止？
5. 是否保持公共 ABI/错误语义兼容，并能用 Mock 覆盖关键失败路径？
6. 命令帧、`if/else`、轮询、`switch`、边界检查和字节序是否满足第 7 章？
