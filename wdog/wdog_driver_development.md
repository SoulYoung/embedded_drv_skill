# WDog 驱动模块开发规范

## 1. 模块职责

WDog 驱动负责配置、启动、关闭、喂狗和请求系统复位。看门狗属于启动链和系统可靠性的一部分，开发前必须确认 Boot 与 App 对看门狗时钟、关闭和析构的约定。

## 2. 必要接口

- `TDrvWDogCreate/Destroy`；
- `TDrvWDogOpen/Close`；
- `TDrvWDogFeed`；
- `TDrvWDogReset`。

用户未明确要求时，仅实现必要接口。窗口喂狗、预中断、调试/低功耗模式、运行时重新配置等能力属于特殊接口，直接增加到 `drv_wdog.h` 的特殊功能接口小节。

## 3. 开发步骤

`demo/drv_wdog.c` 的 `TDrvWDogCfgExTag` 和 `TDrvWDogOpMode` 以当前参考驱动框架为基准，完整保留基址、窗口、时钟源、工作模式、更新许可、窗口与预分频开关成员。目标 MCU 无对应能力时，demo 保留成员并以 TODO 注释说明；平台实现也优先保留该内部配置布局，避免改变对象框架。

1. 确认使用独立看门狗、窗口看门狗或两者中的哪一个；通用 `TDrvWDog` 的默认实现只选择一个明确的硬件对象，不能混用二者的寄存器语义。
2. 确认时钟源、预分频、计数器宽度、超时单位、窗口范围、解锁/刷新序列和更新限制。
3. 确认停止、调试和低功耗模式下看门狗是否运行；若硬件一经启动不可停止，`Close` 只能关闭对象状态，绝不能伪造硬件停止。
4. 确认关闭或析构是否会关闭看门狗时钟，避免 Boot 与 App 的寄存器访问冲突。
5. 以 `demo/drv_wdog.h/.c` 为起点，仅填写配置表、解锁、超时转换、寄存器配置、喂狗序列和关闭/复位 TODO。
6. 验证最小/最大超时、重复打开/关闭、窗口期喂狗、不可更新看门狗和复位行为。

## 3.1 默认启用与重配置顺序

部分 MCU 在复位后默认启动看门狗。此时硬件 `EN` 状态不能用于判断驱动对象是否已经 Open，驱动必须以对象状态为准。

当手册允许重新配置时，`Open` 按以下顺序执行：

1. 在临界区外使能寄存器访问时钟，读取实际时钟频率，计算重装值、窗口值和控制/锁定寄存器镜像，并完成所有范围检查。
2. 在最小临界区内执行手册规定的解锁序列；若可写，先失能当前默认运行的看门狗。
3. 连续写入重装、窗口、状态清除和控制配置，重新使能模块，按配置写锁定值，并完成首次服务序列。
4. 退出临界区后再更新驱动对象的打开状态。

解锁后是否需要读取状态位或轮询，完全以手册规定为准。不可因通用防御性编程假设存在“解锁完成”标志；若手册要求轮询，则轮询必须带超时。

临界区只保护不可被喂狗、中断或其他上下文打断的连续寄存器写序列，不得包含时钟查询、超时计算、参数校验或无关分支。

## 4. 验证清单

- [ ] 时钟频率和超时换算与用户手册一致；
- [ ] 解锁、配置和喂狗序列满足顺序与时限；
- [ ] 窗口模式和预分频组合正确；
- [ ] 未打开、重复打开、重复关闭和非法 index/timeout 返回正确错误码；
- [ ] Boot 与 App 对时钟和析构的约定已验证；
- [ ] 系统异常时能够在预期时间内复位。
- [ ] 硬件不能停止时，Close/Destroy 没有关闭仍在工作的看门狗时钟或伪造停止操作。
