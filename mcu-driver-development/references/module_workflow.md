# 模块开发工作流

## 输入分析

先读取现有模块 `.h/.c`、配置文件、`drv_common`、错误码头文件和依赖驱动。再从用户手册、SDK和芯片头文件确认实例数量、资源映射、时钟、复位、引脚复用、寄存器时序、中断、DMA、错误和限制。

编码前建立“硬件事实表”，至少记录：能力及作用域、地址区间、最小操作粒度、寄存器访问属性、复位值、时钟/时序前置条件、命令顺序、完成与错误条件。每项结论应能定位到手册章节或目标芯片特性宏。厂家 SDK 中被条件编译保护的通用分支只能用来核对流程，不能证明当前芯片支持该能力。

## 通用文档边界

模块开发文档只固化接口骨架、资料核对项、实现顺序和验证方法，不记录特定芯片的名称、寄存器名、IRQ 名称、实例数量、时钟编号或能力结论。这些信息属于目标平台实现依据：以该芯片的用户手册、SDK 和头文件为准，并落实到目标平台的 `.c` 文件或独立的平台适配记录中。

## 设计输出

开发前形成以下清单：

1. 必要接口；
2. 特殊接口；
3. 配置结构和默认值；
4. 对象状态和生命周期；
5. 依赖的本平台公共对象；
6. 错误码和超时处理；
7. 正常与异常验证用例。

## Demo 骨架与接口语义闸门（强制）

每个模块的 `doc/<module>/demo/drv_<module>.h/.c` 是该模块在新 MCU 上开发的默认公开骨架。开始平台实现前，先逐项审计公开枚举和接口的语义能否由目标硬件表达，再复制骨架并填写与 MCU 有关的内容。

必须逐项保留并核对：

1. 文件头、include guard、`extern "C"`、必要/特殊接口分组；
2. 公开类型、对象成员、枚举成员及其既有数值和顺序；
3. 公开 API 的名称、签名、Doxygen 注释、示例和调用顺序；
4. 生命周期、参数检查、错误码、对象状态和源文件的函数组织方式；
5. demo 中已有的空行、缩进、花括号和 `switch` 风格。

demo 与目标芯片冲突时，硬件寄存器语义以用户手册为准，但不得默默把不支持的硬件命令包装成“成功”。接口名称、签名、对象模型和已有接口分组必须保留；仅当枚举本身表示目标硬件的寄存器位、字段编码或通道编号时，平台实现中的数值应直接采用目标硬件编码，并在头文件注释中说明映射依据。应先形成冲突清单，再选择以下一种方式：用软件组合实现原语义；保留接口并返回现有不支持错误码；或经用户确认后修订通用 demo 和所有受影响实现。确需补充目标 MCU 独有能力时，在原有“特殊接口”分组中增加，并完整写出 Doxygen 注释。

完成骨架核对后，直接完成对象定义、生命周期、参数检查、状态管理、通用计算和错误码传递。将寄存器、时钟、复位、端口、IRQ、DMA、SDK 和校准集中到 `.c` 文件的平台适配区；每个无法从资料确认的硬件细节必须以 `TODO` 说明所需资料和完成条件。

## 协议型异步模块的分层与参考继承

通信协议、数据项/报文结构、队列或缓冲状态机、接口调用顺序和回调语义属于通用层。目标平台适配层只负责将这些语义落到外设实例、板级资源、数据搬运和完成来源上。

同类模块的既有实现是协议行为的参考基线。移植时应先完整比对对象成员、状态迁移、函数顺序、注释和回调上下文；除硬件适配替换外，不应无依据地重构协议流程或删除核心数据结构。若目标硬件能力导致协议语义无法保持，必须明确记录差异并选择软件补偿、现有错误码或经确认后的接口调整。

demo 必须保留所有通用数据结构、状态迁移、错误码和完整注释。只把平台有关的寄存器、时钟、端口、DMA、IRQ 和 SDK 调用替换为 `TODO`；每个 `TODO` 要写明需要完成的硬件动作、前置条件或完成条件，不能用删减协议逻辑来回避平台适配。

同一类外设若被多个角色或模块使用，应在公共资源层提供按实例索引的共享资源描述。各角色驱动在创建阶段绑定该描述，而不各自维护私有基址表或重复的实例映射函数；仅单一模块使用的状态仍留在本模块内。

## 公共状态与并发

`drv_common` 只保存至少被两个驱动模块共同使用的资源和状态；仅由单个模块使用的映射、常量或运行状态应保留在该模块的 `.c` 文件中。

临界区以实际资源竞争关系决定，而不是机械地覆盖所有寄存器读改写：

1. 同一寄存器由多个引脚、通道或对象共享，或共享链表、引用计数、状态标志会被并发修改时，必须保护完整的读—改—写或状态转换；
2. 每个引脚、通道拥有独立寄存器或独立字段，且操作仅影响当前对象时，不因读改写本身添加临界区；硬件提供的原子置位/清零寄存器也应直接使用；
3. 临界区只覆盖维持一致性所需的最小操作，例如链表指针更新、引用计数增减、冲突检查与资源占用；配置 DMA、准备缓冲或执行长硬件时序应移到临界区外。确有不可被介入的硬件序列时，才覆盖该完整序列；
4. 已经修改硬件或共享状态后，若后续可失败操作失败，必须恢复已修改的寄存器、引用计数和对象状态，不能留下半打开、半配置状态。

## 异步完成、超时与恢复

异步传输应明确区分“已提交”“正在搬运”“协议完成”“异常待恢复”等状态，并标注每个状态只能由哪个上下文修改。启动流程通常先准备数据和搬运描述，再使能搬运与外设请求，最后发布忙状态、启动超时并对外发出握手；具体先后仍以目标手册为准。

多个完成来源时，每个回调只处理自己负责的完成标志和资源收口。单一方向的数据搬运完成不当然等于总线或协议完成；最终完成条件必须依据接口语义和目标硬件手册合并判定。回调所在的中断或线程上下文须继承 demo 的既有约定，并在注释中明确，不能在不安全的上下文中直接执行会竞争传输状态的恢复流程。

恢复接口必须区分可安全恢复和强制恢复：非强制恢复先证明当前事务已静止，若未静止则不改变硬件和协议状态；强制恢复才执行停止请求、终止或收口搬运、清理外设状态和恢复缓冲状态。静止条件、终止方式和清理顺序由目标平台资料确定；不能因为参考平台使用了某个 DMA 状态或停止接口，就在另一平台无依据地照搬。

## 寄存器与地址安全

1. 为每个被写寄存器确认访问属性和副作用。只有普通可读写寄存器才按需要读改写；清标志、只写寄存器及有读取副作用的寄存器按手册规定的写法处理。
2. 地址与长度校验必须先排除非法值和算术溢出，再检查目标硬件定义的有效区域、对齐及操作边界。半开区间和差值比较是常用实现方式，但应服从项目接口采用的地址表示。
3. 命令型外设先从手册提取完整状态机阶段，再落实目标芯片规定的寄存器顺序。不能把某颗芯片的写使能、参数同步、解锁或清标志步骤泛化为所有命令外设的固定流程。
4. 手册限制代码执行位置时，应验证相关函数、只读数据和回调在操作期间均可访问，并核对链接放置与启动初始化。具体使用 RAM、另一存储区或专用执行区由目标硬件决定。

## 简化实现的边界

优先直接在公开接口中完成单处、短小的寄存器计算和状态处理，避免为单次使用增加无实际价值的私有函数、映射表或重复状态。但是，防止资源冲突的检查、独立且较长的硬件时序、共享资源的引用管理，以及失败后的回退流程不得为了代码短小而删除。是否保留校验或私有函数，应以其能否维护资源一致性、表达独立时序或被多处复用为准。

对可能造成资源半打开、数据损坏、总线失步或不可恢复硬件状态的失败，必须保留错误处理并按项目日志规范上报。对已由配置或调用前提保证、且失败后没有额外恢复价值的低价值检查，不机械堆叠；可依赖统一日志主动报告可诊断的异常。

## 实现顺序

先实现对象创建和配置校验，再填写 Open/Close 的平台资源申请和释放 TODO，之后填写基本读写或控制 TODO，最后实现特殊能力。公开的结果码接口以成功值初始化 `result`，保持单一出口，并在返回错误时按项目日志规范上报；没有失败语义的私有辅助函数不为了形式统一而虚构结果码。

## 验证顺序

依次验证正常调用、空指针、未创建、未打开、重复打开、重复关闭、非法索引、非法枚举、边界值、超时、硬件错误、关闭恢复、销毁后访问以及多对象共享资源。

异步协议模块还应验证两个方向完成的先后顺序、单方向失败、超时、非强制恢复不产生副作用、强制恢复后的重新传输，以及缓冲满/空和连续收发下的状态迁移。

至少对目标模块执行一次启用常用警告并将警告视为错误的独立编译；对 RAM 函数、特殊段或中断向量，再检查链接 map/反汇编，确认代码实际落点和调用目标，而不是只做语法检查。
