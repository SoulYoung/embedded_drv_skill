# MCU Driver Development

## 工作边界

将一个 MCU 平台视为一个独立驱动仓库；不要为多 MCU 共仓兼容而抽象接口。使用用户给出的手册、SDK、芯片头文件、板级配置和已有驱动作为事实依据。

新平台驱动开发以模块 demo、芯片用户手册和官方 SDK demo 为必备输入：demo 定义项目接口骨架、对象模型和代码风格；用户手册定义寄存器语义、时序与硬件限制；官方 SDK demo 用于核对寄存器配置顺序和芯片初始化流程。三者冲突时，以用户手册的硬件定义为准，并保留 demo 的接口外形。

用户额外提供的同模块实现仅作为补充参考。此时继承其公开接口、成员名称、对象模型、调用顺序、注释和格式；只补足用户要求的功能与可验证的边界问题。枚举若直接表达目标硬件寄存器位、字段编码或通道编号，平台实现应以目标芯片定义为准，并在头文件说明映射；其余枚举保持原数值和顺序。不得为了“更通用”重命名、重排枚举或另建无关抽象层。

开始本仓库中既有任务或续接上一次工作前，先阅读 [当前项目续接上下文](references/current_project_context.md)，再读取当前任务涉及的模块资料。

## 必须遵循的规则

- C 源码、头文件和脚本使用 UTF-8。
- 新增 C 函数使用单一出口，以 `result` 统一收口。
- `if/else` 后只有一条语句时不使用大括号；有两条及以上语句时换行并使用大括号。
- 文件级 Doxygen、修改日志和版权信息只放在模块 `.h`；`.c` 直接从自身 `.h` 开始，除非用户已有的同名 `.c` 文件本就保留了其他必要注释。保留 Doxygen 接口注释和现有注释格式；新增接口必须写完整注释。
- 使用项目已有 `hcc_error_code_drv_soc_common.h`，不重新定义公共错误码。
- 公开接口放在模块自己的 `.h`，分为“必要接口”和“特殊接口”。用户未明确要求增加功能时，只实现必要接口。
- 特殊功能直接增加到模块 `.h`；不创建可选扩展层、能力查询层或通用扩展控制接口。
- 当前平台的 `drv_common.c/.h` 是本平台共享对象与驱动依赖汇总处，应按已有方式使用；仅纳入存在共享数据或直接驱动依赖关系的模块头文件，不因模块新增而无差别包含独立驱动。
- 若本平台的 `drv_common.h` 已集中包含芯片库、公共错误码和基础类型，模块 `.c` 只包含自身 `.h` 与 `drv_common.h`，不重复包含这些公共头文件。
- 不猜测寄存器、时钟、复用、中断或 DMA 语义；所有索引、指针、长度、枚举、除数、位宽和状态在硬件操作前检查。
- 父对象按既有语义使用 `c_ref_`、`o_ref_` 引用计数；仅子对象可使用 `is_open_`。若用户给出的同模块实现已有不同模型，先保留该模型并提出差异，不擅自改写。

## 注释工作流

开发、迁移或生成任意驱动模块时，先阅读当前仓库中同模块的参考 `.h/.c`，把注释视为代码骨架的一部分；不得在生成 demo 或新平台实现时为了压缩代码而删除通用注释。

1. `.h` 保留完整文件级 Doxygen、修改日志和版权信息；保留枚举、结构体、字段、回调、公开接口和使用示例的原有注释。结构体私有/公开字段继续使用 `///<` 短注释。
2. `.c` 不新增文件级 Doxygen。迁移时保留原有的函数前注释、`Create/Open/Close/Destroy` 生命周期说明、队列/缓存所有权、并发或中断上下文、状态机转换、异常恢复和调用顺序等通用注释。
3. 只有具体芯片事实才替换：寄存器名、位域、固定地址、实例编号、时钟源、IRQ 向量、SDK 函数以及某芯片勘误。替换位置用 `// TODO: ...` 说明需要依据目标手册填写的内容、限制或验证条件；不得以一个笼统 TODO 替代整段通用软件逻辑。
4. 新增或重写的私有函数必须在函数前说明其职责；新增公开接口必须在 `.h` 写完整 Doxygen（用途、参数、返回值、关键上下文/缓冲区所有权），在 `.c` 保留必要的实现说明。简单赋值、显然的局部变量和重复语句不强制增加注释。
5. 注释应解释“为什么、状态由谁维护、何时可调用”，不重复代码字面含义。尤其标注：回调是否在中断中调用、缓冲区何时由驱动接管、资源的父子引用关系、Close/Destroy 的兜底语义，以及硬件操作的等待/超时要求。
6. 交付前逐项对照原模块：文件头、对象字段、每个公开接口、关键私有函数和关键分支的通用注释均仍存在；检查 demo 中不存在具体 MCU 名、寄存器名、SDK 调用或固定硬件数值。

## 厂家 SDK 的使用边界

厂家头文件用于寄存器基址、寄存器宏、位域宏和芯片常量。除非用户明确要求，禁止调用厂家 SDK 的 `xxx_init`、`xxx_config`、`xxx_enable`、`xxx_get` 等封装函数；驱动不暴露厂家 SDK 枚举类型。直接使用厂家头文件中的宏完成寄存器读改写、状态轮询和频率计算。

## 标准开发流程

1. 阅读 `drv_common`、公共错误码、目标模块现有 `.h/.c`、配置文件、依赖驱动和构建文件。
2. 先从模块 demo 确认目标模块的 `.h/.c`（以及需要时的 `_cfg.h`）骨架、公开接口、对象模型、注释和格式，并审计接口语义能否由目标硬件表达；存在冲突时先列出“软件组合实现、保留并返回不支持、经确认修改接口”三类处理方案，不能默默改枚举或误发硬件命令。
3. 从用户手册确认实例、时钟、复位、引脚复用、寄存器位域、访问属性、时序、中断、DMA、错误与限制；形成可追溯的硬件事实表，再用官方 SDK demo 核对初始化顺序与寄存器配置。SDK 的条件编译通用分支不能作为目标芯片支持能力的单独证据。
4. 若用户另有同模块参考实现，必须同时逐项比对 `.h` 和 `.c`：接口、枚举成员与数值、类型名、对象状态、寄存器访问、时序、错误码、注释和格式；不得只核对源码实现。
5. 先复制目标模块的完整骨架：`drv_xxx.h`、需要时的 `drv_xxx_cfg.h`、`drv_xxx.c`；不删除原有注释，不改历史名称。
6. 在 `.c` 中直接填充寄存器级实现；对尚无资料的硬件细节保留 `TODO`，注明所需资料与完成条件。
7. 按 `Create -> Open -> 使用 -> Close -> Destroy` 实现生命周期，保持已有引用计数和共享资源语义。
8. 依次验证正常、空指针、未创建、未打开、重复调用、非法枚举、边界值、超时、硬件失败和资源释放。

## 寄存器命令与存储区通用规则

- 按手册确认寄存器访问属性；只有访问语义明确允许时才使用读改写，清状态操作按目标寄存器规定的方式完成。
- 地址和长度计算必须避免整数溢出，并按目标硬件实际的连续区域和操作边界校验。
- 命令型外设按手册还原前置条件、参数传递、启动、完成、错误和收尾阶段；各阶段的具体寄存器顺序由目标硬件决定，不从其它芯片套用固定流程。
- 手册限制代码执行位置时，检查完整调用链、只读数据、链接放置和启动初始化，不能只依赖源码中的段属性。
- 轮询默认带超时。厂家 SDK 中的永久等待只能作为时序参考，不能覆盖项目的超时要求。

## Flash 模块专用规则

开发 Flash 时先阅读 `../flash/flash_driver_development.md`、Flash demo、目标芯片存储组织、操作流程、芯片特性宏和官方 Flash 驱动。重点确认操作粒度、地址边界、前置条件、执行位置限制和错误恢复；不能把某颗芯片的命令装载方式或寄存器顺序固化为通用实现。

## Reset 模块专用规则

开发 Reset 时先阅读 `../reset/reset_driver_development.md`、Reset demo、复位源资料、芯片头文件和官方 Reset 驱动。保持公共原因编码稳定，显式适配硬件状态，并在实现前确定原因查询采用启动快照还是实时读取语义；清标志和触发复位均按目标硬件规定实现。

## Clock 模块专用规则

开发 Clock 时必须阅读 `references/clock_register_level.md`、Clock demo、芯片用户手册和官方 SDK clock demo。用户提供的 `user/drv_clock.h/.c` 仅在实际存在时作为补充参考。不得调用厂家 `rcu_*()` 等 SDK 函数。

- 若 `TDrvClockIClk` / `TDrvClockRcmIdType` 使用“寄存器组 × 32 + 位号”的索引编码，完整继承数值；通过该编码直接选择 RCU 寄存器与位号，不转换为厂家枚举，也不建立映射表。
- 系统时钟按资料中的寄存器顺序实现：安全源、清理旧配置、启动并等待源稳定、Flash 等待周期、总线分频、PLL 参数、等待锁定、切换系统源、确认状态、升频保护。轮询必须有超时，禁止永久死循环。
- `TDrvClockGetSrcFreq` 必须通过当前 RCU 位域计算实际频率；不可使用厂家查询函数，也不可仅返回配置常量。
- 没有明确需求或参考实现的平台功能时，不虚构功能时钟支持；保留必要接口并返回已有通用错误码，或保持参考实现已定义的行为。
- `.c` 文件按实际调用顺序组织：能放在调用点之前实现的私有函数，不写前置声明。不要因模板化而集中罗列私有函数声明。
- 只为有独立时序、可读性或复用价值的硬件流程保留私有函数。仅在单一公开接口中使用、且逻辑短小的轮询、频率分频计算或寄存器读改写，应直接放在该接口内，避免不必要的函数调用层次。
- 用户提供的 Clock 模板已有私有函数布局时，优先沿用其数量和先后顺序；不得额外拆分 `GetPllFreq`、`GetSysFreq`、`WaitStable`、`WaitSys` 一类仅供单处调用的辅助函数，除非用户明确要求或该函数确有多处复用。
- `TDrvClockIClk`、`TDrvClockRcmId` 等公开枚举须完整保留参考头文件中的所有成员、编码表达式、最大值和类型名；不能因当前源码暂未使用而删减枚举项。
- Clock 模板中的 `switch` 每个实际 `case`（含 `default`）均使用独立 `{}` 包围处理语句，`break;` 放在语句块之后；多标签共用处理逻辑时，连续标签后只保留一个语句块。此约定优先于通用规范的最简 `case` 写法。

## IRQ 模块专用规则

开发 IRQ 时先阅读 IRQ demo、芯片用户手册、芯片头文件和官方 SDK 的中断示例。IRQ 的职责仅限全局中断嵌套控制和 NVIC 独立中断开关；不注册 ISR、不清外设中断标志、不保存回调，也不擅自增加优先级、向量表或 Pending 控制接口。

- 公开 `UInt8 num` 只接受芯片头文件 `IRQn_Type` 中的非负外设 IRQ 编号；用头文件中最后一个有效外设 IRQ 常量检查上界，禁止将负数内核异常编号传给 NVIC。
- 全局中断使用 `global_ref_` 嵌套计数：0 变 1 时调用内核全局禁止接口，1 变 0 时调用内核全局使能接口。必须防止计数下溢与 `Int8` 溢出；达到 127 时返回现有范围错误码。
- 可直接调用 CMSIS `NVIC_EnableIRQ`、`NVIC_DisableIRQ` 及内核全局中断指令；不得调用厂商 `nvic_irq_enable`、`nvic_irq_disable` 一类 SDK 包装函数。
- Close 只改变对象打开状态，不擅自平衡或恢复已有的全局中断引用计数；Destroy 按项目模板仅兜底调用 Close 并忽略其结果。

## PORT 模块专用规则

开发 PORT 时先阅读 PORT demo、芯片的引脚控制/复用资料、芯片头文件和官方 GPIO 配置示例。PORT 只管理引脚模式、复用、上下拉、输出类型和驱动能力；不负责电平读写和 GPIO 输入中断。

- 对模式、复用、上下拉、输出类型和速度寄存器，只读改写目标引脚字段并写回寄存器；必要时用 IRQ 临界区保护读改写。
- 引脚复用值、GPIO/模拟/复用模式的编码以芯片手册为准。若通用 demo 的枚举无法完整表达目标芯片的复用范围，在保持已有枚举值不变的前提下补充目标平台所需的成员。
- Open 只获取 PORT 实现实际依赖的时钟或共享资源；Close 不复位或关闭仍可能被其他驱动使用的用户引脚配置。
- 不调用厂家 `gpio_mode_set`、`gpio_af_set` 等配置包装函数；仅使用其寄存器与位域宏。

## GPIO 模块专用规则

开发 GPIO 时先阅读 GPIO demo、芯片 GPIO 输入输出和 GPIO 中断资料、芯片头文件及官方 GPIO 示例。GPIO 负责单引脚电平读写和 GPIO 输入中断对象；引脚模式、复用、上下拉、输出类型由 PORT 模块先配置。

- 单引脚电平必须使用芯片提供的原子置位/清零寄存器；读取外部电平使用输入状态寄存器。
- GPIO 输入中断是模块能力，不依赖于芯片是否存在名为 EXTI 的独立外设。按手册确认实际中断路径：它可能是独立 EXTI 控制器、GPIO 内部边沿检测寄存器，或其他 GPIO 中断单元。
- 若目标芯片的同号引脚在多个端口间共用一个中断源，第二个冲突对象必须拒绝打开；若多条 GPIO 中断线共用 NVIC 向量，按向量组引用计数开关 NVIC。
- 对应中断路径的 Pending 按手册规定清除；只能清除本次对象或本次 ISR 已确认的位，不能整寄存器清零破坏其他 GPIO 中断状态。
- 不调用厂家 `gpio_bit_write`、GPIO 中断初始化等配置包装函数；仅使用寄存器、位域宏与 CMSIS NVIC 接口。

## CAN 模块专用规则

开发 CAN 时先阅读 CAN demo、芯片 CAN/CAN FD 手册、芯片头文件和官方 CAN 示例。CAN 负责控制器、收发软件 FIFO、普通/优先发送状态、错误状态与硬件过滤器；不要将不同硬件控制器的消息 RAM 或 IRQ 语义当成通用实现。

- 普通发送 FIFO 与优先发送必须分别维护状态和硬件资源。优先发送只在 `preemptive_state_` 空闲时提交，普通发送仅在 `sending_` 为假且控制器未处于 Bus-Off 时从 FIFO 取帧。
- 将报文收发完成、错误、Bus-Off、波特率侦测拆分为独立私有处理函数。ISR 负责读取/确认本次硬件标志和调用对应处理；回调上下文必须继承 demo 语义并在头文件中说明。
- `Open` 按时钟、端口、控制器、过滤器和中断的依赖顺序执行。每个返回 `Int32` 的步骤仅可在结果严格等于 `kHccDrvSocCommonSuccessLine` 时继续；失败时按相反顺序回退已经取得的资源，不得使用 `>= 0` 判断成功。
- `Close` 必须先禁止外设中断源和 NVIC，再停止控制器、恢复/释放端口和关闭时钟，最后清除软件打开状态。硬件状态轮询必须有超时。
- 位时序、消息 RAM 布局、过滤器编码、错误标志清除与 Bus-Off 恢复严格以目标手册为准；目标不支持的能力保留公开接口并返回已有不支持错误码。

## SPI 模块专用规则

开发 SPI 时先阅读 SPI demo、芯片 SPI 手册、芯片头文件和官方 SPI 示例。先核对帧宽、分频、NSS 时序、FIFO、DMA、错误标志和 IRQ 语义，再决定现有端口模型是否可直接适配；不得将上一芯片的帧控制、FIFO 或勘误限制当作通用硬件事实。

- 多从机事务需要“整笔传输保持 CS”时，必须确认硬件 NSS 的行为；若硬件 NSS 不能表达该语义，使用 GPIO CS，并使 `auto_cs_` 表示驱动自动操作 GPIO。
- 公开帧宽、波特率和传输长度的取值必须受目标硬件限制；不能支持的公开值返回现有不支持错误码。
- 全双工发送期间必须按手册处理接收数据，避免接收溢出；IRQ 状态机需同时处理发送可写、接收非空、传输结束和硬件错误。
- 默认 ISR 仅推进状态机、清硬件状态和记录完成事件；用户回调在非 ISR 上下文执行。若项目已有接口必须 ISR 回调，先由用户确认该例外。

## WDog 模块专用规则

开发 WDog 时先阅读 WDog demo、芯片用户手册、芯片头文件和官方 WDog 示例。先明确本模块实际管理独立看门狗还是窗口看门狗；通用对象未要求扩展时只实现一个硬件对象，不能将两者的时钟、计数器、窗口或中断语义混合。

- 超时单位、预分频和装载值必须由用户手册的实际时钟频率、计数器宽度和公式计算；不得仅使用 SDK 配置函数或猜测固定常数。
- 必须区分硬件复位后的模块状态与驱动对象的 `is_open_` 状态。硬件默认使能不等同于驱动已打开；若硬件允许重新配置，`Open` 应按手册先解锁并失能当前模块，再应用本次配置。
- 对可重配置的看门狗，先在临界区外完成时钟频率读取、超时/窗口范围校验及寄存器值计算；临界区只覆盖解锁、失能、连续写配置、重新使能、锁定和首次服务序列。不得为手册未定义的解锁完成标志增加轮询；手册明确要求的状态轮询必须有超时。
- 启动、解锁、配置和喂狗必须严格使用手册规定的序列；若手册规定连续喂狗间隔或低功耗前等待时间，应在接口注释和模块文档中明确。
- 启动后硬件不能停止的看门狗，`Close` 只关闭驱动对象状态，`Destroy` 仅兜底调用 Close；禁止写无效的停止位、关闭仍被看门狗使用的时钟或声称硬件已关闭。
- 仅在用户明确需要时增加窗口喂狗、提前唤醒中断、调试暂停、低功耗行为或运行时重新配置等特殊接口。系统复位可直接使用 CMSIS 内核复位接口，不调用厂家 SDK 包装函数。
- WDog demo 的 `TDrvWDogCfgExTag` 和 `TDrvWDogOpMode` 完整继承既有参考驱动的成员布局；目标 MCU 无对应能力时保留成员并标注 TODO，平台实现也优先保留该内部配置框架，不能仅因当前硬件未使用而删减。

## TimerSrv 模块专用规则

开发 TimerSrv 时先阅读 TimerSrv demo、模块工作流、芯片定时器手册、芯片头文件和官方定时器示例。TimerSrv 是软件定时项与系统时间基准服务，不是普通定时器外设的直接抽象。

- 必须确认周期寄存器的装载、计数方向和超时语义；周期、频率和高精度计数均按实际寄存器语义计算，不能假设重装值等于周期时钟数。
- 高精度读取必须取得软件tick和硬件当前计数的一致快照，并检查硬件超时Pending；最大计数来自重装寄存器而非实时计数寄存器。
- 定时项创建会修改服务对象的索引和数量，必要时直接使用项目既有全局IRQ嵌套保护。默认每个 TimerItem 由一个调用方独占时，不为启停和改周期接口额外加锁；同一对象跨线程共享由调用方同步。
- 若既有公开接口已规定回调在ISR执行，保留该接口语义，并在模块文档和头文件明确其不可阻塞、不可等待的限制。
- Open必须校验时钟频率、重装值和中断资源；任一步失败均回退已开启的控制器、IRQ和时钟。
